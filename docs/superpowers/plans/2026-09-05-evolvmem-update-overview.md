# EvolvMem 开发计划：主动召回成功经验、场景适配与持续改进

日期：2026-09-05。状态：2026-09-06 已完成实现、正式切换和验收。本文件接替上午的五阶段简版计划。
目标：用户自然描述问题时，助手主动找回相关成功经验，按新场景调整，依据真实结果更新经验，并能跨会话继续任务。
架构：复用 Context Core、SQLite、FTS/HNSW、现有模型调用与 MCP；当前 Agent 理解场景并制定行动，EvolvMem 保存和检索经验与证据。
范围：先在 Codex + evolvmem 项目完成闭环，再验收 Kimi、DSH；覆盖此前的写入正确性、项目归属、摘要、检索和续接需求。
约束：可信内网、1～10 人、单机单进程；保留现有依赖与部署。只维护这一份计划，不预写实现代码；不新增安全专项、分布式服务、模型训练或前端主题重做。

## 一、最终使用方式

用户描述业务问题或故障 → Agent 自动查询相关经验 → 核对成功证据和适用条件 → 提出符合当前场景的方案 → 执行已授权工作并验证 → 保存结果与适用范围 → 下次更准确地选用。
“自动”包括检索、整理与有证据的反馈记录；历史方案不能扩大当前用户任务授权。“越聪明”体现为选得更准、解释得更清楚、少重复错误，效果由验收集衡量，不承诺每次使用都提升。
方案取舍：选择“现有 Agent + 公共经验服务”；每句话额外调用一个模型判断是否检索会增加等待与费用，单靠一次性启动注入又覆盖不了中途换话题。使用任务变化触发和会话内去重。

## 二、经验如何保存、召回和改进

### 经验记录

每条经验保存：问题与目标、当时的项目/环境/约束、采用步骤、为何有效的解释及其依据、实际结果、验证范围与来源、适用/不适用条件、更新时间、派生关系。
复用 experience/playbook 类型：L0 描述“解决什么问题、关键条件”；L1 按固定字段保存步骤与验证；L2 保存详细说明和来源引用。经验不再受普通事实“200 字单句”限制，仍遵守现有分层预算。
最小新增模块 experience_service.py 负责上述结构校验、写入和经验查询；不把业务规则继续堆进适配器。
成功记录分清“技术验证通过”“业务结果达成”“用户确认有效”；Agent 自称已完成、用户未回复、某条无关测试通过均不构成成功证据。只记录实际验证覆盖的步骤，推测的有效原因注明推测。
先整理 evolvmem、Eva、蓝鲸中最多 20 段有来源的历史处理过程，来自现有记忆、会话摘要/归档和修复记录；证据不足则保留候选，不凑成功数量。先出明细再在开发验收中应用，保留原始记录。

### 主动触发

| 场景 | 自动行为 |
|---|---|
| 新会话出现实际任务 | 从当前任务与工作区获取项目背景，并查相关案例 |
| 会话中换项目、换任务或新增明确问题 | 用新任务、约束与必要近邻对话重新查询，不等待“查历史”命令 |
| 诊断出现新证据、采取的办法失败 | 更新问题描述，查相似失败和替代成功案例 |
| 用户说“继续”“接着做” | 先恢复任务检查点，再查下一步需要的经验 |
| 用户确认结果或纠正做法 | 关联本轮实际使用的经验，记录证据或适用范围变化 |
| 简单确认、闲聊、相同任务重复表达 | 不重复查询；没有合适经验就正常处理当前任务 |

MCP 服务本身不能自行看到尚未传给它的新对话：必须同时修改客户端规则和实际调用路径。Codex 通过 MCP instructions 和项目级任务规则触发；Kimi 用 MCP 规则及已有会话 hooks；DSH 将已有 pre-step 从仅启动注入改为按新任务触发。各端分别用工具调用记录验收。
项目不明时先解析用户明确提到的名称与工作区绑定；仍不明确则仅查全局方法或询问必要项目线索，不把 home 目录名当业务项目。
新增 experience_recall(project, query, constraints, workstream_id?) 返回经验 ID、短内容、验证级别、匹配依据、不适用条件及来源；同任务首次 context_session_start 已包含足够经验时复用结果。
同项目案例优先；跨项目复用只面向标明可迁移的方法及抽象条件，保留来源项目；不把别的项目地址、配置、业务事实当成当前事实。
关键词与向量共同召回，候选前限定项目与有效状态；向量过滤不足时扩大候选；L1 补充细节命中。先通过相关性/条件判断，再按独立成功证据、近期验证、失败和纠正排序。
默认最多采用 3 条经验，共享现有经验注入预算；无合适结果不补满。相同任务与证据版本缓存，新增约束、失败或话题变化失效；不为触发判断单独调用模型。

### 如何结合新场景

Agent 对每条候选比较“问题机制、目标、环境、约束”，判断可复用步骤、必须改变的步骤与待验证假设；相似报错不能直接当成相同根因。
真正采用历史方法时，用简短自然语言说明“参考哪次做法、当时什么条件下成功、本次改变什么”，并保留经验引用；仅提供背景且不影响方案时不重复汇报检索过程。
本轮修改形成派生案例，保存 parent_experience_id 和具体条件差异，保留原成功案例及版本；只有明确纠正同一事实时才建立替代关系。

### 如何越用越聪明

一次有明确来源的成功可以成为“已验证案例”，仅在对应条件下复用；不要求先重复成功两次才允许回忆。无证据内容仍为 candidate，不作为成功案例自动注入。
调整现有统一“两份 archive 才晋升”规则：区分单次已验证案例与重复验证的方法；跨客户端统一以独立任务及验证记录计数，兼容已有 archive 来源。至少两次独立成功且无未解决反证，才提高“重复验证”级别。
新增 experience_record 接收结构化案例及来源摘要/引用；扩展 context_record_outcome 传入 source_id、任务/运行标识、验证标识、经验版本与反馈类别。服务端绑定合法来源；证据不再因 MCP 参数缺失而无法晋升。
在现有 context_sources/context_evidence 上补必要字段及去重键：同一经验版本 + 同一任务验证事件只计一次；重试、跨 Agent 转述和重复提炼不得生成第二份成功。纠正同一事件用修订关系重算，不额外累加。
反馈至少区分：成功、方法在适用条件内失败、场景不适用、与新证据矛盾、结果未知。场景不适用更新条件并在该场景降权；无关执行故障或结果未知不处罚原方法；真实反证降低对应版本可信度。
结果只关联本轮实际采用且得到验证的方法；仅被检索到不算使用，使用不算成功。用户说“这次可以”须结合正在验收的任务，不能给所有召回项统一加分。
改动后的方案在新场景验证成功后，保留为有自身证据的派生案例；归纳共性时保留成功条件和例外，不能因相似就覆盖原案。
复用 context_playbook：至少 3 个相关、经验证且来自至少 2 个独立任务的案例才尝试归纳方法；先核对机制与适用条件，不仅凭 L0 相似度。新归纳仍标为待验证，不继承“已经实际成功”的次数。
候选方法仅进入明确的验证流程；回放旧案例是相容性检查，不算新的独立成功。通过针对适用条件的验证后可限定范围使用；自然任务中的实际结果继续决定其可信度。
失效方法保留原因并停止常规推荐，其派生总结同步重新评估；命中/使用频率只作统计，不以“经常被查”代替效果证据。历史原文到期时保留必要证据摘要、引用与验证范围。
