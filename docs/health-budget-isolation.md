# 后台健康检查的分阶段预算

后台检查先完成物理完整性检查，再执行资料、来源与索引一致性检查。
原实现从打开连接时启动语义 SQL 的 60 秒进度预算；独立物理检查若耗时超过
60 秒，后续语义 SQL 即使刚开始执行也会被中断。

现在前置元数据观察保留原有 60 秒 SQL 预算与工作线程关闭信号检查。
物理检查返回后，重新启动后续语义 SQL 的 60 秒预算。
身份、配置、文件基线、检查前后版本核对与失败拒绝策略保持原有约束。
全库检查完成后的最短刷新间隔仍为 30 秒；期间的数据变化合并等待。

该预算由 SQLite progress handler 执行，不是整个检查的硬截止时间。
物理检查自身、阻塞 I/O 以及不执行 SQLite VM 指令的操作不受这 60 秒限制；
本次修改也不表示这些操作已提速。

回归用假时钟分别验证前置元数据观察超过 60 秒仍被拒绝、物理检查耗时
125 秒后仍可进入语义检查，以及后续语义 SQL 自身耗时超过 60 秒仍被拒绝。
线上先前的物理阶段耗时样本用于定位问题，
不作为新版本性能验收数据。

## 轻量版本读取的失败诊断

revision 查询仍使用独立只读连接，保留 100 毫秒 SQLite busy 等待与
250 毫秒进度预算。现在失败记录附带固定阶段、数值 SQLite 错误码与预算
回调是否实际触发，以区分锁忙、主动中断、打开失败及其他错误。
诊断不记录 SQL、数据库路径、令牌或异常正文，也不增加重试或放宽权限。
只有 SQLite 返回 INTERRUPT 且该请求的回调确实发起中断时才标记预算超时。

本批相关回归共 109 项通过；1280/1440 桌面工作原理流程检查通过。
这些检查不代表 10–20 人并发或完整 PostgreSQL 迁移已经验收。
