# 从业务需求到系统图集与 EvolvMem 设计确认

本说明整理本会话关于系统程序设计、业务分析、图种与绘图顺序的讨论，并持续记录 EvolvMem 的需求确认。设计基准已确认：先明确用户需要的目标，再核对现有实现，分别标清已实现与差距。完整图集经用户确认后，才提炼为一个可复用 skill。

## 一 先分析业务 再选择图

设计的主线是：谁遇到什么问题 → 希望得到什么结果 → 业务怎样完成 → 谁负责各环节 → 数据怎样变化 → 系统怎样实现 → 如何验收 → 怎样部署运行。

每张图应回答明确的问题。图集围绕业务目标组织，关键步骤、判断、人工交接、输入输出和异常去向都能找到位置。完整不等于把所有图种都画一遍，也不等于把全部细节塞进一张大图。

| 阶段 | 先分析什么 | 主要图与产物 | 为什么在这里做 |
|---|---|---|---|
| 1 目标与范围 | 谁使用、解决什么问题、负责什么、不负责什么、成功标准 | 系统边界图、目标与范围清单 | 边界决定后续工作范围 |
| 2 需求分析 | 用户怎样完成一件事、参与者职责、业务规则和例外 | 业务流程图、泳道图、用例图与用例规约；按需页面原型、数据流图 | 把目标转成可以讨论和验收的行为 |
| 3 概要设计 | 功能分工、系统组成、外部依赖、主要接口 | 功能模块图、架构图 | 每项需求都要有明确的责任模块 |
| 4 数据设计 | 业务实体、关系、来源、归属、版本、有效性 | E-R 图、数据字典、逻辑表结构；细化数据流图 | 避免业务概念混淆以及保存与使用脱节 |
| 5 详细设计 | 执行步骤、分支、并行、交接、调用和状态变化 | 活动图或程序流程图、时序图、状态图；按需类图、判定表 | 明确模块内部如何兑现业务规则 |
| 6 编码与局部验证 | 一个业务闭环能否运行、局部规则是否正确 | 代码、单元测试、同步更新的设计图 | 尽早检验设计是否可实现 |
| 7 集成与验收 | 模块连接是否正确、用户目标是否达成 | 测试用例、需求追踪表、实际结果；必要时测试流程图 | 测试覆盖用户目标才有验收意义 |
| 8 部署上线 | 实际运行位置、连接方式、配置、访问入口、恢复方式 | 部署图、发布步骤、上线检查结果 | 测试环境通过后仍需验证正式入口 |
| 9 运行维护 | 实际故障、新需求、资料与图是否过时 | 更新受影响的图、需求和测试 | 让设计说明持续对应当前系统 |

这是依赖顺序，可以迭代。数据流图从需求阶段开始；数据和架构共同推敲；部署约束可在概要设计时提出；验收条件从需求阶段开始定义。编码、测试和验收不需要为了形式增加新图。

## 二 各种图分别回答什么

| 图 | 核心问题 | 绘制要点 |
|---|---|---|
| 系统边界图 | 系统与哪些人或外部系统交换什么 | 系统内外清楚，标明主要输入输出 |
| 用例图 | 谁通过系统实现哪些目标 | 参与者、业务目标与关系；细节写用例规约 |
| 业务或程序流程图 | 一件事按什么步骤推进 | 开始结束、处理、判断、异常和返回路径 |
| 活动图 | 活动如何组织与控制 | 动作、条件、分支、并行与汇合；按业务需要使用 |
| 泳道图 | 谁负责哪一步、何处交接 | 按角色或系统划分责任；通常是带责任分区的活动图或流程图 |
| 数据流图 DFD | 哪些数据经过什么处理、进入什么存储 | 外部实体、处理、存储、数据流；箭头表示数据，不表示控制先后 |
| 功能模块图 | 功能怎样划分、各部分负责什么 | 职责明确，主要功能有归属 |
| 架构图 | 主要组成怎样连接 | 服务、组件、存储、外部依赖及其连接 |
| E-R 图 | 有哪些业务实体、它们怎样关联 | 实体、属性、关系和基数；再转逻辑表结构 |
| 时序图 | 一次操作中谁先调用谁、返回什么 | 参与者、消息、返回、等待及必要异常分支 |
| 状态图 | 一个对象有哪些状态、什么触发迁移 | 区分对象状态与操作步骤，明确转换条件与失败去向 |
| 类图 | 代码对象有哪些职责、接口与关系 | 用于需要表达类或接口结构的设计，不强行套用所有项目 |
| 部署图 | 程序实际运行在哪里、怎样连通 | 机器或运行节点、进程、存储、连接与用户入口 |

结构化详细设计也可使用 N-S 盒图、PAD 图、判定树和 PDL 伪代码；它们按问题选用，不与所有流程图重复绘制。用例描述用户目标，测试用例描述输入、操作和预期结果，两者通过验收条件关联。

## 三 怎样逐项分析业务

每个业务场景依次核对以下内容，采用用户可理解的名称；接口名放在需要追查实现的位置。

1. 目标与参与者：谁在什么情境下遇到什么问题，希望得到什么结果。
2. 触发与前提：什么事件启动业务，执行前必须具备什么资料或状态。
3. 正常路径：从开始到业务完成，每一步做什么、由谁负责。
4. 输入与输出：数据从哪里来、发生什么变化、交给谁、保存在哪里。
5. 判断与例外：规则如何判定；空结果、信息冲突、归属不明、重复与失败怎样处理。
6. 自动与人工：哪些系统自动做，哪些需要用户决定，决定如何反馈到后续业务。
7. 数据生命周期：来源、归属、版本、修改、撤回、删除和派生产物的处理规则。
8. 验收：用什么代表性场景、具体输入和可观察结果证明业务达成。

每轮只讨论一个主题，先给出当前理解和依据，再提出不确定项。用户原话、助手建议、现有实现分别标记；沉默不算确认。可由代码和运行结果查明的技术事实由助手调查；业务选择、矛盾和无法证实的事项交给用户确认。

确认后的要求建立关联：需求 → 业务场景 → 图中节点或关系 → 数据或接口 → 测试用例。后续修改时同步受影响的关联内容。

## 五 图集的检查标准

- 每张图说明主题和适用范围；现状与目标清楚区分，未确认项不画成已落实事实。
- 重要业务能从触发走到结果；人工判断、异常和恢复路径明确。
- 关键箭头标清动作或数据；控制流、数据流、调用和实体关系不混用。
- 同一个业务对象在不同图中名称、责任、状态和关系一致。
- 需求有对应场景与验收条件，关键图节点有业务依据；现状结论有调查证据。
- 先完成业务内容审阅，再检查图形是否可读、可导航和可导出。
- 正常字号、通俗文案；详细内容按主题展开，不堆小字或把技术接口当作业务名称。
- 交付保留可编辑图源和可浏览成果；完整图集通过用户最终确认后才进入 skill 制作。

## 六 行业参考与方向选择

2026-10-11 调研：以下为公开机制与案例，涵盖企业知识管理、知识服务方法和 Agent 记忆工具，不作为统一排名，也不代表已在 EvolvMem 验证有效。

| 参考对象 | 官方资料说明的做法 | 对本次设计的启发 |
|---|---|---|
| Glean | 人员确认资料准确和最新，显示确认人及时间，支持重审提醒与过时标记。[验证机制](https://docs.glean.com/user-guide/knowledge/verification/how-verification-works) | 知识应体现确认依据与当前状态 |
| Guru | 可配置内容规则与使用反馈驱动的自动核验、撤销核验；保留负责人、质量记录与人工纠正。[内容验证](https://help.getguru.com/docs/verifying-and-unverifying-cards) | 日常维护、异常处理和人工责任可以分别设计 |
| KCS v6 | 区分工作中、未验证、已验证和归档；使用过程中审阅改进；再由知识领域专家从案例模式提炼更高层知识。[状态](https://library.serviceinnovation.org/KCS/KCS_v6/KCS_v6_Practices_Guide/030/040/010/030)、[提炼](https://library.serviceinnovation.org/KCS/KCS_v6/KCS_v6_Practices_Guide/030/040/010/042) | 分开保存案例与归纳方法，按实际需求维护知识 |
| Zep 与 Graphiti | 派生事实关联原始来源，维护多来源关系，记录有效和失效时间，失效事实保留历史。[来源追踪](https://www.getzep.com/blog/how-zep-tracks-provenance-in-agent-memory/) | 追踪支持与反驳依据，保留变更历史和适用时间 |
| LangMem | 区分事实知识、经历和行为方法，支持结合交互反馈更新指令。[核心概念](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/) | 自我进化需要影响后续做法，并检验这种改变是否有效 |

落地参考：Red Hat 公开案例介绍了按问题相关性重排知识、生成摘要，以及从支持记录生成符合 KCS v6 标准的文章草稿。[Red Hat 案例](https://www.redhat.com/rhdc/managed-files/rh-red-hat-ai-powered-innovation-it-support-case-study-1579684-202412-en.pdf)。这是厂商公开案例，本说明不把其成本收益数字外推到 EvolvMem。

下表为调研后给出的方向比较。用户已选择 C，A、B 保留作比较；C 下的具体规则仍逐项确认。借鉴机制不等于必须安装这些产品。

| 方向 | 核心行为 | 收益与代价 |
|---|---|---|
| A 先建立可信知识库 | 明确来源、版本和可用状态，持续整理与纠正；自动归纳新方法后续再展开 | 业务规则较容易解释，但当前阶段对第三项自我进化目标支持有限 |
| B 先建立自动更新记忆 | 优先从对话维护事实、项目状态和历史关系，遇到变化更新当前记录 | 自动积累和更新较充分，开发方法是否有效仍需另建验证流程 |
| C 按开发结果持续改进（已选择） | 保留来源和历史，将具体案例与归纳方法分开；按实际采用结果修正适用条件，通过独立场景检验新方法，再逐步扩大复用 | 最贴近三项已确认目标；已有机制保留，具体差距与调整逐项确认 |

C 的建议细化：原始记录保留原话；偏好以用户明确表达核对；环境事实看对应版本与实际状态；具体经验保留问题、条件、行动和结果；归纳方法关联支持案例、反例和适用边界。不同类型不用同一套“成功”标准。

保存、检索为线索、当作已验证方法采用、推广为通用做法，是不同用途。提议记录有条件支持、结果未知、不适用、反驳或过时等事实；一次有效只支持当时条件，多次独立结果才支持更广范围，不能用固定复用次数代替判断。

使用经验后的反馈需区分“被检索到”“实际采用”“相关验证通过”；重复摘要或同一事件的多份记录不当作多份独立支持。新归纳仍是待验证结论，不能因 AI 自评、受欢迎或被多次引用就自动成为确定规则。

拟议维护方式：日常核对和记录自动进行，冲突或适用范围变化触发复核，业务含义及偏好仍由用户裁定；自动维护不扩大执行操作的授权。新方法保留旧版并用未参与提炼的代表性场景检验，具体启用与撤回规则需继续确认。

拟议验收关注：相似任务是否更容易完成、重复错误是否减少、错误建议是否增多、新归纳在新场景是否有效、需要用户额外判断的次数与等待成本；指标目标以后逐项确认。此处仅为设计建议，未改动程序、正式知识或服务。
