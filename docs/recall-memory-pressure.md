# 召回检查的内存与重复工作优化

本次包含三项范围有限的修复：减少价值评估期间无用的原文保留，消除初次初始化内的重复检查，并延长连续失效的能力索引恢复轮次之间的等待。这些改动不迁移数据库，不改变项目分类和原文存储，也不降低召回的来源、资格与证据要求。

1. **价值评估缓存只保存证明哈希。** `capability_assessment._rows_read` 仍对每个来源执行当前读取，同一次调用内仍只读一次。此前缓存保留每份读取结果中的完整原文、角色与状态，后续实际只使用 `proof_hash`；现在仅保存哈希和独立的来源缺失标记，并立即释放临时完整结果。来源不存在与哈希值为空仍按原语义区分，损坏的证明结构仍报错。来源版本、原文证明、来源印记、单元证明、策略及历史评估检查不变。该改动不压缩或删除存放的原文，也不跨请求沿用缓存。

2. **首次初始化共享同一轮观察。** `ContextService.initialize` 保持依赖、数据库与索引的原初始化顺序，仍先执行 `_refresh_health()` 再返回 `status()`。这两步在本次调用内共享投影、向量与计数检查结果；首次物理完整性检查和文档结构核验仍执行，未初始化的向量仍不能使 PRIMARY 模式提前就绪。共享范围在成功或异常退出时恢复，后续独立状态查询不复用此次结果，其他模式与同参数再次初始化的行为保持不变。

3. **连续失效的能力索引恢复单独退避。** 当一轮恢复中任一资料空间返回 `status=partial` 且 `stale` 为正整数时，计入独立的连续失效次数。默认轮次结束后的等待依次为 **60、120、240、480、900 秒**，之后保持 900 秒；这不是单次恢复的执行超时。没有该类失效的一轮会重置此计数，普通未完成批次不因此延迟。原失败退避保留，同时存在时采用较长等待。每个资料空间的报告原样返回，`dirty`、`ready`、待处理数量和已处理结果不被改写；证明不完整的内容仍保持待更新。任务不会因此被删除，也不会把失效核验当作成功。

能力召回仍保留候选资格及最终选中来源的检查；经验召回仍沿用原资格、项目范围、适用条件与验证证据链，并在查询前后检查对应资料空间的后台准入。其他 Context 操作仍沿用原检查。以上三个补丁不扩大后台准入的适用范围。

验证包括该评估缓存不再让完整原文对象跨来源存活、原判定与读取次数一致、首次初始化真实重复扫描的反例、四种模式与异常清理、退避时序和多资料空间报告不变。集成验证记录：三个补丁合并后的 Linux 原生回归 **255 项通过，33.99 秒，测试进程峰值 266.9 MiB、swap 为 0**。这些数字描述测试运行，不代表生产召回延迟或生产服务内存上限；发布后的运行观察仍须单独记录。

本次修复的是已确认的额外保留与重复工作，**尚不能证明全部 OOM 原因已消除**。它没有完成 PostgreSQL 迁移，也没有完成十几人并发或读写延迟 SLO 验收。源码回归通过与生产效果验证分别记录，不以测试结果替代现场证据。


## LAN 完整性检查的统一管理

LAN 托管开始提供服务前，为每个资料空间显式设立一个物理检查所有者。常驻 Context 服务与后台健康状态读取同一份已提交数据的完整性记录，不再各自启动定时扫描。启动时原来的首次完整检查仍执行；交接不把未绑定新所有者与配置指纹的旧成功直接当成新基线。已在运行的旧扫描实际退出后才开始新扫描，旧扫描晚到的结果不能覆盖新状态。

记录绑定数据库路径、设备与文件标识、已提交结构版本、配置指纹及协议，并有单调递增版本。物理检查结束时立即发布；失败会撤销原成功并使请求健康缓存失效，无需等后面的语义检查。所有者关闭或确认边界变化后不自行恢复，也不退回前台重扫。物理成功不能清除语义检查错误、伪造完整就绪或刷新旧诊断。

事务仍执行自己的真实完整性检查，不能借用其他连接的已提交成功；同时遵守已确认的关闭、边界异常或物理失败。事务中的临时结构变化不发布成全局结构状态，回滚不会因此永久损坏共享证明。非 LAN 构造及独立 Web 保留原生命周期。

保留原最长五分钟有效期和提前刷新条件；缓存命中不会续期。这项改动消除重复所有者，但不保证耗时过长的下一轮一定赶在到期前完成，也不证明冷启动或所有内存压力已解决。扫描日志只记录开始、结束、耗时、匿名数据库标记和固定结果类型，不记录正文、SQL、路径或配置内容。原文、数据库迁移与向量内容均不因本项修改而变化。
