# LAN background diagnostics and bounded capability admission

The first health stage moves complete Context diagnosis off the LAN capability request path. The production HTTP host starts one diagnostic worker for the fixed namespaces. It owns read-only SQLite connections, ContextService instances and native vector handles. It does not encode, rebuild indexes, migrate data, or modify resident request services. A consistent SQLite transaction identifies the exact semantic generation evaluated.

`memory_status(detail="health")` is an authenticated LAN-only additive detail. It retains identity, argument, owner and space validation, and does not take the business dispatch lock. The existing revision detail and full status response remain unchanged. Standalone MemoryMCPServer retains its original gates and schema. A direct LanTools adapter that has not started background hosting retains its original synchronous capability gate; its health detail explicitly reports a missing baseline. The HTTP lifecycle starts health alongside capture; runtime close stops publication and lets an in-flight worker release its own resources. Stdio clients forward to the HTTP host rather than owning a second LAN runtime.

| Field | Meaning |
| --- | --- |
| `diagnostic.last_checked_ready` | Result of the last complete scan, not present global readiness |
| `diagnostic.codes` | Whitelisted, content-free diagnostic codes |
| `evaluated_generation` | Semantic generation of the complete read snapshot |
| `observed_generation` | Latest independently observed committed generation |
| `freshness` | `current`, `stale` or `unavailable`; diagnostic freshness only |
| `completion_age_seconds` | Age of the last completed scan |
| `refresh_pending` | Queued or in-flight work for this namespace |
| `diagnostic_error` | Stable background failure code, or null; the status query itself succeeded |
| `hard_gate` | `allowed` or a stable reason why this baseline cannot admit capability search |

Ordinary semantic changes queue a refresh without revoking otherwise valid capability results. Missing baselines, physical failure/expiry, failed scans, and database/schema/configuration/mode/model changes fail closed. Neither health nor capability requests perform a repair scan. Database identity and the startup hard contract are pinned: a changed hard contract requires a correctly reinitialized runtime and a new background baseline, because resident connections/model resources may still describe the old contract. Recreating identical schema definitions changes the SQLite schema cookie but may establish a new baseline after the definition digest is verified; it does not require changing business resources. Config validity is checked independently from semantic diagnostic readiness. Known resident physical-integrity failures also revoke admission. Physical checking reuses the existing identity-validating read-only checker. The worker retains successful physical proofs only for the same database identity and schema, reusing the original check timestamp across semantic evaluations. It rescans at the existing 60% TTL refresh threshold, on identity/schema change, after a failed attempt, or when a current-identity resident failure is known; the default maximum TTL remains 300 seconds. Failed results are never cached as success, and a failed/exceptional refresh removes the old success before retry. The request hard gate still expires the original physical timestamp and preserves current resident failures. Shutdown clears the worker cache and prevents an in-flight check from publishing into an old lifecycle. Native vector loading and complete semantic scan scheduling are unchanged.

Capability search uses catalog schemas at both LAN contract-resolution sites and keeps the shared business lock. Original retriever/index source, assessment, role, vector and ownership proofs remain intact. Before returning, the new LAN path rechecks at most 20 selected candidates in one owned read transaction, including current capability content, source eligibility, assessment, project/module, expiry and required Context layers, current body hashes and selected legacy projection/mapping consistency. Native Context sources do not require a legacy mapping. Selected migrated sources require a unique existing mapping, matching derived layers, status and supersession links; dependency expansion is capped at 500 IDs/peers and rejects if exceeded. Invalid source-backed results are excluded; malformed required structure rejects the response. The extra final bounded source revalidation can reread selected source bodies, and is deliberately retained until profiling and an equivalent version-based proof justify reducing it. It never scans all Context rows. Capability results include `health` with the same explicitly last-checked semantics; its nested diagnostic failure retains the `error` field. The standalone health-detail response uses `diagnostic_error` so a successful status query (including pending or failed diagnosis) has MCP `isError=false`; invalid arguments and actual tool errors keep `isError=true`. A final hard-boundary observation rejects a boundary changed during retrieval.

The worker coalesces requests by namespace, runs at most one full scan, selects the least recently served eligible namespace to prevent long-scan starvation, and enforces a default five-second per-namespace retry cadence. Idle namespaces refresh within 30 seconds (or earlier based on integrity TTL). A scan publishes its completed generation even when a later semantic commit has occurred, preserving a useful last-checked result; subsequent refresh converges after writes stop. SQLite full-scan statements have a 60-second progress deadline. The reused separate physical checker and native index loading are not forcibly interrupted; shutdown may return while they finish, but cannot close their resources or publish an old lifecycle result.

Other Context reads and writes retain their existing synchronous full-health gates. Full status can still scan, ordinary business dispatch remains serialized, and this release does not claim general request concurrency. Independent-library PostgreSQL migration remains future work. Original data, source versions and human decisions are preserved.

Operational verification uses temporary SQLite fixtures and event barriers: lightweight status while business/diagnostics block, committed snapshots, lifecycle isolation, candidate withdrawal/structure failures, hard-boundary refusal, and revision regressions. Production deployment, browser screenshots and restored-backup verification belong to the deployment runbook, not to unit-test success.

## Capability index snapshots and short recovery gates

Capability recovery, incremental synchronization and vector lookup share the recovery file gate. Heavy source/value checks now run outside both file locks and SQLite write transactions. Recovery briefly takes the recovery gate and shared-cache gate to copy durable vector and proof bytes, then restores an owned native index outside the gates. It cannot auto-refresh or share mutable handles with a resident cache. Initial repair selection remains advisory so concurrent uploads do not prevent safe per-item progress.

Final recovery certification checks a read-only database snapshot against an owned index snapshot. Before publishing, it checks the original database connection, file identity, schema, data version, total changes, embedding contract and temporal boundaries. It also compares both index/proof file identities and strong content digests under the publication gates. A concurrent vector-only save, proof replacement or source change keeps the index dirty and returns partial/stale; it cannot certify old work as ready. Successful certification alone clears dirty debt.

Incremental synchronization performs its initial source check and post-encoding recheck in owned read snapshots. Encoding stays outside all locks. The short publication transaction validates the post-encoding fence before merging the update into the current durable proofs. Borrowed caller transactions are refused before waiting for the recovery gate and are never committed or rolled back by the index operation.

Search uses an independent vector/proof image with one coherent SQLite read snapshot. A later index save cannot mutate that query's image. This is snapshot read semantics, not a guarantee that no write can occur after the snapshot starts. Current LAN selected-result validation remains unchanged. Legacy vectors without proof entries keep their existing transitional lookup behavior and never count as certified recovery coverage. Ranking and candidate budgets are unchanged.

Content-free traces distinguish recovery initial/final audits, synchronization initial/final source proofs, file-gate waiting/holding and query eligibility. Eligibility is no longer a child of the held-file-gate timing. Tests use real temporary files, native indexes, separate SQLite connections and event barriers; they verify query completion while audit work is paused, file replacement and source withdrawal races, cleanup after errors, and competing writers. Ordinary LAN business dispatch is still serialized; this change does not establish multi-user PostgreSQL concurrency.
